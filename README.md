# StalzoneArtTracker

Локальный веб-инструмент для анализа аукциона артефактов в игре **STALCRAFT**. Сервис сам собирает данные с публичного API аукциона, считает справедливую цену и ликвидность каждого предмета и подсвечивает в браузере лоты, которые выгодно выкупать и перепродавать.

> **О доступности кода**: репозиторий временно открыт для ознакомления (например, для рекрутера/работодателя). После просмотра он может быть снова переведён в приватный режим — если ссылка перестала открываться, значит доступ закрыт, напишите мне и я открою заново.

## Что делает проект

- Непрерывно опрашивает API аукциона STALZONE и копит историю продаж и снимки активных лотов.
- На основе истории считает для каждого сегмента предмета (id + качество + процент артефакта) **справедливую цену** и **ликвидность**, с учётом затухания веса старых продаж во времени.
- Для каждого активного лота считает потенциальный профит, ожидаемое время продажи и итоговый score — насколько лот привлекателен для выкупа.
- Отдаёт всё это на локальную веб-страницу с live-обновлением через Server-Sent Events — без перезагрузки страницы видно новые лоты и пересчитанные показатели.
- Позволяет прямо на странице менять параметры аналитической модели (окна, пороги, формулы) и пересчитывать всё на лету.

## Архитектура

Проект — три независимых синхронных Python-процесса, обменивающихся данными через SQLite и HTTP, плюс статический браузерный фронтенд.

```
src/collector.py   → тянет данные с API аукциона в SQLite (история продаж + активные лоты)
src/brain.py       → аналитика поверх этих данных: fair value, ликвидность, профит, score
src/server.py      → HTTP-сервер: отдаёт сайт, JSON-API и SSE-уведомления браузеру
web/               → фронтенд на чистых HTML/CSS/JS (без фреймворков)
```

Данные текут в одну сторону: `collector` пишет в SQLite → помечает изменённые предметы «грязными» → `brain` пересчитывает только их и кладёт результат в кэш `auction_scores.sqlite3` → `server` джойнит кэш к активным лотам и через SSE говорит фронтенду «данные обновились».

Подробное описание каждого модуля — в docstring в начале соответствующего файла (`src/collector.py`, `src/brain.py`, `src/server.py`).

## Технологии

- **Python 3** (stdlib `http.server`, `sqlite3`, `threading`, `concurrent.futures`) — без веб-фреймворка, сервер и многопоточность написаны руками.
- **requests** — синхронные HTTP-запросы к API аукциона с ретраями и рейт-лимитом.
- **SQLite** — три отдельные базы под разные роли данных (история / активные лоты / кэш расчётов).
- **Server-Sent Events** — realtime-обновления на фронтенде без WebSocket и без фреймворков.
- Ванильные **HTML/CSS/JS** на фронтенде.

## Запуск

```bash
git clone https://github.com/Fox3s-Py/StalzoneArtTracker.git
cd StalzoneArtTracker
pip install -r requirements.txt

cp .env.example app_config/.env
# и вписать в app_config/.env свои CLIENT_ID / CLIENT_SECRET от API аукциона

python src/collector.py   # сборщик данных (можно с --once)
python src/brain.py       # аналитика (можно с --once)
python src/server.py      # веб-сервер, откроется на http://127.0.0.1:8000/
```

Проекту нужны собственные `CLIENT_ID`/`CLIENT_SECRET` для доступа к API аукциона — без них `collector.py` не запустится (см. `src/config.py`).

## Статус

**Проект остановлен в августе 2026.** Он работает и использовался лично для
отслеживания выгодных лотов, написан полностью самостоятельно, без шаблонов и
генераторов проектов. Но развитие прекращено осознанно: доводить его дешевле
переписав, чем дорабатывая.

Что не так с текущей версией — по моей же оценке:

- **Нет тестов вообще.** `brain.py` считает справедливую цену, ликвидность и
  score по нетривиальным формулам с затуханием веса старых продаж — ровно тот
  код, который без тестов страшно менять. Любая правка формулы требует ручной
  перепроверки результатов на глаз.
- **Архитектура сложилась стихийно.** Три процесса, обменивающиеся через три
  SQLite-базы и флаг «грязных» записей, — это решение выросло по ходу работы,
  а не было спроектировано заранее. Работает, но связи между модулями неявные
  и держатся на договорённостях, которых нет в коде.
- **Сервер на `http.server`.** Написать HTTP-сервер и многопоточность руками
  было полезно один раз, чтобы понять, что происходит под капотом фреймворка.
  Для дальнейшего развития это тупик.
- **Нет CI, линтера и фиксации версий зависимостей** — `requirements.txt`
  без версий означает, что через полгода проект может не собраться.
